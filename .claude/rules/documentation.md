# Documentation rules

The README is regenerated by `/readme` from the code; its template is
`.claude/skills/readme/references/readme-template.md`.

## README must contain

1. What the product does (one paragraph) and a feature list.
2. Architecture overview with a Mermaid diagram and the request flow.
3. Tech stack and prerequisites with minimum versions (Go, Node/npm, Docker, optional tools).
4. Quick start (Docker Compose) and local development setup.
5. How to run the backend and the frontend, separately and together (`make dev`), with ports.
6. Configuration: every environment variable, default and meaning (backend and frontend).
7. API reference: each endpoint with method, path, request/response schema, status codes,
   and copy-pasteable `curl` examples **with the real responses they produced**, including
   at least one error example. Link to `backend/api/openapi.yaml`.
8. Testing: how to run unit, component, API and browser tests; coverage numbers from
   `docs/coverage.md` and how to open the HTML reports.
9. Project structure (short annotated tree).
10. Design decisions and trade-offs (links to `docs/adr/`), assumptions made, known
    limitations and possible next steps.
11. Troubleshooting for the likely problems (ports in use, missing Playwright browser,
    Docker not running).

## Rules

- Facts come from the code and from commands you ran in this session, never from memory.
  Every command and example in the README has been executed; responses are pasted as
  returned (pretty-printed JSON is fine; request IDs may be shortened).
- Write for an engineer seeing the repository for the first time: task-oriented headings,
  short paragraphs, fenced code blocks with language tags, relative links that resolve.
- Plain, precise language. No marketing adjectives, no emojis, no filler, no placeholders.
- Keep the README about the product and how to work on it; tooling configuration for AI
  assistants (the `.claude/` folder) is outside its scope unless the user asks otherwise.

## ADRs (`docs/adr/NNNN-kebab-title.md`)

```markdown
# NNNN. Title in the imperative

- Status: Accepted
- Date: YYYY-MM-DD

## Context
What forces are at play (requirements, constraints, options considered).

## Decision
What we decided, stated plainly.

## Consequences
What becomes easier, what becomes harder, follow-ups.
```

Write one for each decision that a new engineer might question: dependency policy, API
shape and error model, data representation, state management, container topology,
testing strategy. `docs/adr/README.md` indexes them.

## OpenAPI

- OpenAPI 3.1, `info.version` matches the API version, every operation has
  `operationId`, summary, request/response schemas, examples and the problem-details
  responses it can return (shared `components/responses`).
